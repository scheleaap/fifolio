5 · Building block view

The static decomposition. Level 1 is the crates of the workspace. Level 2 opens fifolio-core, where all the domain logic lives.

Status is taken from the code and PLAN.md at commit c04362c. The two binaries are still stubs that exit with "not implemented yet". Most of the built code is the domain model, storage, and the shared import framework. Dependencies at level 2 are read from the use crate::… statements, not from intent.

5.1 Level 1: the workspace

Why this decomposition

  • One writer, one implementation of FIFO. Only the server opens the database, and only the core computes. Two clients could never disagree about a figure. ARC-003 ARC-005
  • The core has no HTTP and no terminal. Every rule is testable in process, without a server. A test checks this mechanically against Cargo.lock. ARC-002 ARC-024
  • The client does not link the core. Linking it would pull SQLite into the client binary. The cost is that response types are defined twice. DEC-018

5.2 Level 2: inside fifolio-core

Why this decomposition

  • Types are kept apart from behavior. The domain model modules are "types only": they define shapes (the transaction sum type, the manual entry shapes, the entities) and nothing persists or computes there. The rules live with the modules that own them.
  • What every format shares is written once. The import framework scopes identity to the account, assigns order across the file, drops non-position rows and counts. An Importer implementation only answers per-format questions, so no format can forget a shared step. DOM-042 DOM-043
  • Storage is a boundary with teeth. storage::codec is the only path from a decimal into a column, and it refuses a value that is not at its scale. Each transaction variant gets its own table, so no nullable column stands for "not applicable here". ARC-010 DOM-010
  • External services are ports. RateFeed hands over the ECB document and RateTable answers rate lookups, so FX is tested against fakes and recorded fragments. TST-020 TST-021
